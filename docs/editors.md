# Editor support

The pinned container and `ashaiy` CLI own builds, formatting, and validation.
Editor settings are adapters; schema targets come from
`config/schema-associations.json`, with VS Code associations generated by
`ashaiy config generate`.

## VS Code

Reopen the checkout in its Dev Container and select `/usr/local/bin/python3`.
Use **Run Build Task** for a book, **Run Test Task** for automation, and
**Run Task** for strict checks, Lean, generation, and site preview.
LaTeX Workshop previews into `vscode-build/`; CLI PDFs live in `build/<slug>/`.
Choose Workshop's strict recipe for repository log validation.

Formatting on save uses Ruff, the repository TeX wrapper, and shfmt.
Problems matchers link Lean, TeX, shell, and repository diagnostics to sources.
Test Explorer uses unittest discovery. Generated caches are excluded from
search and file watching.

Pylance supplies interactive Python analysis; CI uses ty. These are different
analyzers. Select the container interpreter and use `ashaiy check source` for
the authoritative repository gate rather than expecting identical diagnostics.

## Other editors

Edit source files on the host and run the same container commands:

```sh
./scripts/toolchain/run_container.sh
CMD='ashaiy format tex --check && ashaiy check source' ./scripts/toolchain/run_container.sh
CMD='ashaiy book build --book linear-algebra --check --strict' ./scripts/toolchain/run_container.sh
```

Use the [terminal setup](developer-workflow.md#terminal-containers) to install
the Dev Container CLI without VS Code. No second native TeX or Lean installation
is required. Container logs go to stderr, leaving command stdout available for
editor integrations. Keep build output and caches at their designated paths.

For a terminal editor's TeX formatter, send input through
`scripts/latex/format_tex.py --stdout <temporary-file> --source <original-file>`
inside the container. This preserves book-local macro ownership. Do not invoke
latexindent alone: the repository wrapper also preserves literal Lean and
normalizes supported macro arguments.

Run the Lean language server with `lake serve` from the container's `lean/`
directory. An editor outside the container must translate file URIs between
host and container paths, or use a remote editing session. Passing host file
URIs to the container server unchanged is insufficient. Editor-specific host
LSP mappings are examples to validate locally, not part of the verified CLI
contract. Preserve UTF-8 identifiers and avoid applying generic text formatters
to Lean literals.

PDF viewers should open the CLI output on the host. SyncTeX from a container
can contain container paths; configure the viewer's source-path mapping before
expecting inverse search to open host files.

## Integration check

For a new editor or container profile, verify saving UTF-8 text, formatting a
temporary section with its original source path, building a book, opening a
diagnostic at its source location, Lean completion/diagnostics, and opening the
PDF. Check source URI and SyncTeX mappings separately. The automated suite
checks CLI contracts and generated editor settings; it does not drive native
editor interfaces or certify every extension version.

A local smoke check exercised Vim UTF-8 saves, the repository formatter with
a book-owned source path, and container Lean LSP initialization/completion
capabilities and error URI/range reporting. Native GUI extensions, host LSP
URI translation, viewer inverse search and assistive technologies require their
own integration review.
